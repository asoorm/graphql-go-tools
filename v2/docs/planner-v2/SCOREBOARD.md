## Executed-truth results (M1.5 router-level harness)

Plan-level PASS means the plan is *shape-correct*. The executed-truth milestone runs planv2's
plans through the **real resolve engine against real subgraphs** for the first time, to surface the
runtime-contract defect class that plan-shape checks cannot see (precedent: the FetchPath discovery).

**Wiring path taken (fallback).** The primary path -- building Cosmo's router with a go.mod `replace`
to this checkout and wiring `planv2.NewPlanner` into `router/core/operation_planner.go` -- hit a hard
**version-skew wall**: Cosmo `main` pins `graphql-go-tools/v2 v2.12.1` and uses APIs absent from this
branch's 2.11.0 base (`astnormalization.InlineArgument`, `NormalizeNamedOperationWithResult`,
`resolve.Context.InlineArguments`); no Cosmo router revision ever pinned 2.11.x (it jumps 2.9.2 ->
2.12.1), so the `replace` cannot compile. Per the harness charter, we took the authorized lighter
path: **execute planv2 plans through this repo's own `execution/engine` against the real
`execution/federationtesting` subgraphs** (accounts + products + reviews Go GraphQL servers with real
data and golden expected responses). Opt-in via `PLANV2=1` env var at the engine's planner seam
(`execution/engine/execution_engine.go`, drop-in `planv2.NewPlanner`; subscriptions and planv2
errors fall back to v1). This change stays UNCOMMITTED (harness vehicle, not a planv2 fix); the patch
is recorded in the router report.

### Runtime-contract defects surfaced

- **DEFECT 1 -- `GraphQLResponse.Info` left nil (FIXED, commit `10c3b38a`).** The resolver
  dereferences `response.Info.OperationType` unconditionally (`resolve.go` `ResolveGraphQLResponse`),
  so every planv2 plan nil-panicked the resolver before any fetch. `lower` never set `Info` at either
  `SynchronousResponsePlan` site. Fixed to set `Info.OperationType` (matching v1 `plan/visitor.go`);
  regression test `TestLowerPopulatesResponseInfo`. Invisible to plan-level parity (Info is not part
  of the compared response shape) -- exactly the class this harness exists to catch.

- **DEFECT 2 -- planv2 fetches carry no executable transport (OPEN; headline finding).** With Info
  fixed, execution now panics one layer down at `loader.go:1981` (`source.Load`, `source` nil).
  planv2 `lower` sets `DataSourceIdentifier` (subgraph name) but never sets
  `FetchConfiguration.DataSource` (the `resolve.DataSource` loader), and its fetch `Input` is
  `{"body":{"query":...}}` with **no `url`/`method`** (the httpclient wire fields the `Source` reads).
  Root cause: `plan.Configuration` is consumed by `hypergraph.Build` and deliberately not retained, so
  `lower` has no subgraph URL/HTTP client to attach. v1 gets both from the datasource planner's
  `ConfigureFetch()`. **planv2 plans are shape-correct but non-executable as-is.** Proper fix (M1.5/M2,
  larger): retain per-subgraph transport (URL, method, headers, client factory) through to `lower`,
  attach a `Source` to every fetch, and emit `Input` in httpclient wire format. A harness-side bridge
  was ruled out -- the graphql datasource's URL lives in an unexported `Configuration.fetch` field with
  no accessor, so bridging would require editing production packages (out of scope).

**Honest comparison: plan-level 152/181 in-scope PASS vs executed 0/22 correct responses.** The gap
is entirely DEFECT 2 (one systemic transport-lowering gap), not 22 distinct bugs: every plan planv2
produces is shape-valid but lacks the executable transport wiring. This is the executed-truth
milestone working as designed -- it converted a green plan-level scoreboard into a precise,
single-root-cause runtime finding.

  (`histories:null`).
- **422 Unprocessable Entity on deep union nesting** -- `Complex_nesting`, `More_complex_nesting`,
  `More_complex_nesting_typename_variant`.

**Why not fixed here (scope).** The batch-fetch flag is a plan-SHAPE change; wiring it regressed the

and would need regeneration (~25 cases). That is a dedicated lowering-correctness wave owning the
plan-level scoreboard, not the transport wave. Three narrower same-class fixes (top-level-list `@`

are **executed-neutral** while the batch gap dominates and are entangled with it -- so they were
reverted to keep this wave purely additive (zero plan-shape delta). They are the opening moves of the
batch wave. See `m15-transport-report.md` for the full triage.

  planv2 SEARCH returns `*ErrNoValidPlan` ("obligation 3 unreachable"), an **I2 goal-reachability
